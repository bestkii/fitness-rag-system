      01 / SYSTEM ARCHITECTURE
      More than a prompt.
      An auditable workflow.
      
        
      Each layer solves a distinct problem: popularity is not evidence, retrieval is not an answer, and generation is not approval. Every important intermediate state remains inspectable.
      
      
      
      
      
        
      01 / DISCOVER
      ⌁
      Trend discovery
      Finds possible English-language fitness questions from public Mastodon hashtag timelines.
      Mastodon APIOn demand
      
        
      →
      
        
      02 / RESEARCH
      ⌕
      Dual academic search
      The agent plans two queries, searches PubMed and Crossref, removes duplicates, checks topic relevance and assigns source tiers.
      PubMed APICrossref APIPolicy
      
        
      →
      
        
      03 / RETRIEVE
      ⌘
      Dual RAG evidence layer
      The synthetic benchmark uses BGE + ChromaDB; the private textbook pilot uses character TF-IDF because it performed better on that development set.
      512-d BGEChromaDBTF-IDF
      
        
      →
      
        
      04 / GENERATE
      ✦
      Structured generation
      Produces a title, body, five-card script, source markers and review warnings. The English template works without a model key.
      DeepSeek optionalTemplate fallback
      
        
      →
      
        
      05 / APPROVE
      ✓
      Human approval gate
      Review the original sources before approving a draft. The English workbench can then export it or publish an explicitly reviewed Bluesky preview.
      PydanticState machineAT Protocol
      
      
      
      
      
        
      DECISION 01
      Why two retrievers?
      This is an evaluation decision, not technology stacking. Dense retrieval won on the synthetic benchmark; character TF-IDF reached 100% page-range Hit@3 on the small textbook development set.
      
        
      DECISION 02
      How does publishing work?
      Draft approval unlocks a separate post preview. The editor reviews its exact wording and research links before sending it to Bluesky.
      
        
      DECISION 03
      How is private material protected?
      Textbook PDFs, OCR text, vector data and review records stay in ignored local directories. They never enter web search or cloud-generation context.
      
      
      
    
      

    
      
      
      03 / EVALUATION
      Technology choices driven by evidence,
      not buzzwords.
      The two corpora have different properties, so the system uses different retrieval approaches. Every metric states what it measures — and what it cannot establish.

      Metric boundaries
      The synthetic metric measures topic-pair retrieval relevance. The textbook metric measures whether a target page range appears in the Top-3. Neither establishes answer quality, medical correctness or clinical validity.
      
    
      

    
      
      
      04 / OWNERSHIP & SCOPE
      What I implemented —
      and what the system does not claim.
      
      
      
        
      MY IMPLEMENTATION
      Engineering work
      • FastAPI endpoints and Pydantic input validation
      • PubMed / Crossref adapters and source-ranking policy
      • BGE + ChromaDB and TF-IDF retrieval paths
      • OCR quality gates, page provenance and local review state
      • Draft state machine, citation checks and export gate
      • Automated tests and a release guard
      
        
      EXPLICIT BOUNDARIES
      Honest limitations
      • Not a medical diagnosis or clinically validated system
      • Academic abstracts are research leads, not full-paper evidence
      • No automatic Xiaohongshu publishing or engagement actions
      • Private textbook content is never sent to third-party services
      • Content quality, cost, latency and engagement remain unevaluated
      • The synthetic benchmark is not a real-world medical knowledge base
